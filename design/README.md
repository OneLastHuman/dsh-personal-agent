# 项目进展面板 · GUI 设计方案

> 这是交付给请求者的方案说明。设计稿见 [mockup.html](mockup.html)，整页截图见 [shot-full.png](shot-full.png)。

## 一句话

把「概览」页从「几个数字拼起来的仪表盘」改成一条**固定的五段流程**：来信 → 评估 → 执行 → 交付 → 结束。每个 Ticket 是停在其中一段里的一枚标记，颜色表示它需要谁动手。一眼看完，再决定点开哪一个。

## 为什么现在不够

现在的概览页只有四块：等待你处理、系统问题、24 小时数字、执行器负载。它能回答「谁在等我」，但回答不了「事情整体走到哪一步了」。后一个问题得点进「执行」页，一页一页翻。

这不是设计得不好的问题——它守着一组很硬的规矩（[docs/005-panel.md](../../docs/005-panel.md)）：每个数字必须等于它链接到的列表长度，健康状态不占空间，概览只做摘要不重复细节。这套规矩是对的。问题是它把「进展」本身挤掉了。

## 设计取向：仪表盘的反面

如果按常见的做法，大概会长成一张 SaaS 仪表盘：一排等宽卡片、每张一个数字加一个渐变色块、右上角一个圆角折线图。那样的东西放在任何产品里都成立，因此也说明不了这个产品。

这个产品真正特殊的地方是：**它是一个在替人干活的东西，它的状态本质上是「走到哪了」和「需不需要人」。** 所以这次的设计不从「指标」出发，而从「一次工作经过哪些阶段」出发。

具体取舍：

- **不做指标卡。** 数字留在它该在的地方——每一段流程行的右端。
- **不做折线图。** 不用时间序列装饰「好看」，只用一条按比例分段的横条表达「整体像什么」。
- **颜色只有语义，没有装饰。** 绿=完成、蓝=进行中、橙=等你、红=出错、灰=排队/结束。除了橙色（唯一会打断人的颜色），其他都不抢注意力。
- **对照关系要能读出来。** 流程行里每枚标记的颜色，就是它所在那一段的颜色；横条里每一段的颜色，也是同一个语义。三处颜色指向同一件事。

## 页面结构（自上而下）

1. **流程行**——五段，每段一行。左端是段名，中间是停在这一段的 Ticket 标记，右端是这一段的计数或容量。空段显示一行灰字，不占额外空间。
2. **接下来该你**——只有当有人需要动手时才出现。每条给出标题、一句话摘要、它在哪一段、多久之前。这是唯一点击即行动的地方。
3. **系统问题**——只有出错时才出现，压成一行，右侧「去修复」。
4. **点开一枚标记**——就地展开，因为读者刚看的就是它的位置。展开后是 Ticket 详情，重排了优先级：最上是 Worker 最新一次报告，下面是三个小格（上下文用量、工具调用、已过时间），再下面是各自的推进条。
5. **流程横条 + 执行器时间条**——单独一节，回答「整体像什么」。

## 五段流程与现有状态码的对应

设计不新增状态，只重新排布现有的 `ticketStage`：

| 段 | 对应的现有取值 | 什么时候停在这里 |
|---|---|---|
| 来信 | 已接受的 Trigger、已完成的 Eval | Ticket 刚被创建 |
| 评估 | `evaluating`、`evaluating` 超时 | 规则正在判定，或判定失败等人处理 |
| 执行 | `working`（含 queued）、`person/answer`、`person/delivery`、`blocked`、`failed` | Worker 在跑、在排队，或停在等人答复 |
| 交付 | `person/review` | 报告 ready、PR 已开，等人确认或合并 |
| 结束 | `ended` | 已合并、已关闭、被人叫停 |

「评审」（机器人提意见的轮次）不单独占一行，它是「交付」里的一个子状态——只在开完 PR 之后才出现，单独成行大多数时候会是空的。

## 两条硬规则

1. **数字 = 它指向的列表。** 点「等你 2」跳到执行页并带上筛选，跳过去的列表必须正好是这两条。多一条是筛选错了，少一条是数字算错了。
2. **比例要写出分母。** 流程横条的色块会随时间滑动，所以横条必须把时间窗（默认 7 天）和总数写在旁边，否则读者会以为数字的意思变了。可在 24 小时与 7 天之间切换。

## 视觉规格

全部取自 DeepSeek Harness 现有的 `--dsw-alias-*` 设计令牌，不新增色相，深浅两套主题共用同一组语义名。完整色板、字阶、间距、动效规格见设计稿第 07 节。

- **语义色**：成功 `#22c55e`、进行中 `#4176e6`、等你 `#f59e0b`、出错 `#ef4444`、排队/空闲 `#adb2b8`
- **字阶**：只有六档（22/600、15/600、13.5/400、12/400，加两档等宽用于数字与 PR 号），不再增加
- **圆角**：14px 面板 / 10px 内卡片 / 7px 标记
- **动效**：只有「进行中」左侧小圆环匀速旋转；数据刷新淡入 120ms，不做跳动；系统开启 reduced-motion 时全部停掉

## 落地顺序

每一步都能单独交付、单独看效果。

1. **流程行 + 流程横条**——只用现有数据（`GET overview`、`GET threads`），后端不改。
2. **点标记就地展开 + 详情重排**——用 `GET tickets/:id` 现有字段。
3. **补时间维度的数据**——「等你的时长」「工作与等待的比例」现在没有存，需要后端在 assignment 上记录开始与结束。**这是唯一改后端的一步。**

## 这次不改动

- 侧边栏六个标签页，位置与名字都不变。
- 设置页、来源页、对话页的内部结构不动。
- 执行、重试、暂停这些按钮的行为不动。
- Flow 的既有定义（收到、筛掉、评估、接受）保留，只是不再占据概览的主位。

## 待决策

1. **流程行是概览的全部，还是只占上半屏？** 当前设计是前者——流程行就是概览的主体，下面的「接下来该你」附在流程行之后。
2. **五段还是六段？** 当前是五段（评审并入交付）。六段的代价是这一行大多数时候是空的。
3. **要不要保留原来那排 24 小时数字？** 当前设计把它们收进了「来信」「评估」两段的右端，不再单独成块。如果保留，概览会重新变成两部分。
4. **点标记是就地展开，还是跳到执行页？** 当前是就地展开。跳到执行页的好处是只有一个详情实现；就地展开的好处是读者不需要离开上下文。
5. **「等你的时长」这一步现在做还是以后做？** 它需要后端记录时间，也是唯一改后端的一步。
