# 任务路由的 GUI 设计方案

> 这一版回应「要更科技一点，更像分支 / 路由」，并且把「路由」理解成**任务路由**：一条消息进来之后怎么被分派出去，而不是侧边栏标签页之间的跳转。

## 路由实际发生在哪里

读 `src/core/intake.ts` 与 `src/core/model.ts`，一条消息要过四道判断才定归属：

| 顺序 | 判断 | 代码 | 否的后果 |
|---|---|---|---|
| ① | 来源是否监听它 | `scope.scope(trigger)` | 记为 `disposition.filtered`，后面全不发生 |
| ② | 是不是人发的 | `trigger.human` | 影响能否唤醒已结束的 Ticket、能否算人的追问 |
| ③ | 落在哪些讨论串 | `thread.subscriptions[]` | 可能命中 0 个、1 个或多个串 |
| ④ | 有没有 Ticket 认领 | `followupOwners` | 没有 → 走 `queueForEval` |

④ 是真分支：`followupOwners` 排除三类——退回的、只做上下文跟随的（`thread.context`）、正在评估的。剩下的才算认领。

## 真正的两个分叉

1. **一个串挂多个 Ticket。** `github:128` 同时订阅了两个 Ticket，一条消息会同时投递给两个，各自决定怎么处理。人发的消息还能唤醒已结束的那个。
2. **自己的串 vs 只读的串。** `thread.context` 里的串只做上下文，消息到达它但不归它决定。所以「命中订阅」不等于「归它」。

终点互斥：投递到 Ticket、交给评估、被丢弃，一条消息只落进其中一处。

## 设计取向

- **深色为底。** 现有的 DSH 令牌偏扁平，做不出「科技感」；这次在其上叠了一层深色语义色，但色相仍取自既有令牌（绿 / 蓝 / 琥珀 / 红 / 紫），不另造品牌色。
- **科技感只花在三处：** 分叉徽标的渐变、正在流动的虚线、working 节点的呼吸灯。其余保持安静。
- **图是纯 SVG。** 一个 viewBox 管所有坐标与字号，容器多宽图就缩多宽，连线与文字永不错位。没有自动布局，不会因为状态变化整张图乱跳。

## 两个界面

1. **全局管线**（第 1 节）：四道岔排成一条横向流水线，右侧是三条互斥的去处，下方是那两个真实分叉的特写。
2. **单条消息的轨迹**（第 3 节）：展开某条 Trigger 时，显示它自己走过的 T0 → T3。这才是常规用法——不会把所有消息都画成图。

## 三条硬约束

- **互斥**：一条消息的最终结果只有一种，图上不会同时出现两条终点。
- **可下钻**：每个节点点开都落到现有页面（`execution/:id`、`trigger/:key`），没有新路由。
- **不重算**：图只读 `disposition` 里已经落盘的结论，不在前端重新推导一次路由。

## 落地顺序

1. 单条消息的路由轨迹 — 数据全在 `disposition` 里，不改后端。
2. 终点状态 — 接上 Ticket 当前 stage。
3. 全局管线 — 用 24 小时真实计数标注每一道岔的通过量。
